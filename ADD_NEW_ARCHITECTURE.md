# adding a model architecture

## llama.cpp: gguf conversion and runtime

Use [llama.cpp PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696) as the concrete DeepSeek-V4.1 example. The PR remains open as of 2026-10-20, though its current body includes a separate converter and runtime graph; it is not released support. In a runtime-status comment, the author reports a text-only path, a 16k context cap because the two-level candidate mask is missing, and no corpus NLL comparison. A separate review identifies a silent bug in the reviewed head: compressed layers can lose the indexer's selected top-k and attend to all compressed rows once the source exceeds its top-k capacity. Treat these as qualification gaps, and verify fixes on the PR head before relying on it.

### conversion and gguf schema

1. Register the Hugging Face `model_type` / architecture in `conversion/__init__.py` and implement a model-specific converter, reusing the nearest existing converter only where tensor semantics truly match. The PR subclasses the V4 converter, promotes parameters nested under `text_config`, and handles the V4.1 config field that V4 assumes exists but V4.1 omits (`num_hash_layers`).
2. Give the model a distinct GGUF architecture and an explicit list of the tensor families it actually writes. Add the corresponding architecture metadata and tensor names in `gguf-py/gguf/constants.py`. Do not add V4.1 tensors to V4's schema or route a V4.1 file through the V4 loader: the PR found that the overlapping names let an incompatible file partially load without a clean error.
3. Read quantization block sizes from the checkpoint metadata. V4.1's FP8 scales use 32×32 blocks where the inherited V4 path assumes 128×128; the wrong assumption silently rescales weights. Map V4.1's indexer and Engram tensors explicitly, and omit V4-only tensors absent from this checkpoint.
4. Stream very large tensors during conversion. Each Engram table has about 384 million rows; dequantizing a whole table to float32 would require roughly 393 GB for one table. The PR reads row blocks, applies the table's distinct per-row scale layout, and accumulates converted output in a disk-backed memmap. Preserve this bounded-memory behavior in any new converter path.

### runtime graph and serving

1. Add a separate architecture dispatch, hyperparameter reader, tensor loader, and graph (the PR uses `DEEPSEEK41` and `src/models/deepseek41.cpp`). Reuse shared V4 compressed-stream/KV helpers where their contracts match, but keep V4 behavior and tensor definitions unchanged.
2. Derive layer roles from the tensors present in the file, then implement V4.1's actual graph: sparse-compression ratios 0/1/2 and source-layer reuse; index keys from the shared KV latent; no extra query-head RMS norm after `wq_b`; lagged hyperconnection mixing; and Engram's per-layer hash tables, token map, prime buckets, offsets, and start padding. These are semantic requirements, not optional optimizations: several wrong variants still produce fluent output.
3. Carry the selected top-k from each index-source layer to the compressed layers that reuse it, and verify the carry names the expected source. The PR's review says the submitted head can instead fall back to a full causal mask after the source exceeds `index_topk` rows. Also implement and test the two-level candidate mask before claiming contexts beyond the PR's stated 16k limit.
4. Add the model's chat template and parser for its DSML tool-call tags; test exact tag spelling, including the leading spaces in V4.1 names. Add draft-model loading and `n_swa = 0` handling only if speculative decoding is in scope; these are separate from ordinary model loading.
5. Validate conversion by reading every emitted tensor and checking shape, type, and representative values. Validate the graph against the official reference with a small deterministic fixture that exercises every layer role, then cover long prefill, chunked prefill, incremental and batched decode, tool calls, and any enabled image or draft path. Specifically test top-k reuse beyond its selection capacity and the two-level candidate boundary. A fluent smoke prompt is not evidence of graph parity.

## redqueen custom runtime: official checkpoint and hip path

DeepSeek-V4.1-Flash-1017 is already implemented in redqueen's custom runtime. The worker executes the pinned official inference graph and adds validated HIP kernels and bounded checkpoint readers around it; it is not a GGUF loader. For this deployment, “full precision” means the official checkpoint path rather than the Unsloth Q2 GGUF: the released checkpoint still contains its specified FP8/FP4 formats, which the worker handles explicitly.

### architecture source and checkpoint mapping

1. Make the official inference implementation the source of truth. Pin and inventory the model code, image processor, configuration, tokenizer, and checkpoint revision; update the expected revision and checksums together. The worker verifies these files before executing them. Do not copy the llama.cpp graph into a second Python graph.
2. Extend the pinned reference graph and config only when the new architecture requires it. The worker constructs `ModelArgs` and `Transformer` from that pinned source on a meta device, then applies the configured single-session context. Add any new layer state to the session-state plan and reset path so model state is accounted for and cleared correctly.
3. Update the checkpoint mapping audit before loading payloads. Add explicit source-to-graph names, aliases, and permitted dtype casts; reject unknown, duplicate, missing, or shape-incompatible tensors. Then extend the dense load planner for the actual dtypes, scales, scratch buffers, and peak memory. Keep the metadata audit ahead of allocation and verify representative loaded values afterward.
4. Give oversized architecture state its own bounded access path. Redqueen already leaves routed experts and the two giant Engram tables out of the dense resident load: experts are read into a bounded FP4 cache, while Engram rows are read on demand in bounded batches. Add analogous streaming/cache logic for new oversized tensors rather than materializing them as dense weights. Include host buffers, device copies, and transient conversion space in the reservation estimate.

### hip acceleration, memory, and qualification

1. First run the pinned reference path as the correctness baseline. Add a native HIP operation only after profiling identifies a useful target. Keep its Python wrapper in `python/kernel.py`, implementation in `src/*.hip`, and build entry in `build.sh`; preserve the reference operation's dtype, layout, masking, and reduction behavior. Unsupported checkpoint formats must fail explicitly rather than silently changing numerics.
2. Wrap optimized graph pieces reversibly, as the current worker does for the tiled indexer, tiled hyperconnections, Engram row reads/forward, cached MoE, RMSNorm, and RoPE. Keep each optimization independently switchable so failures can be bisected against the pinned baseline.
3. Update memory planning and the model-router worker profile whenever weights, context state, expert/table cache behavior, or transient peaks change. Admission must happen before allocation; hold the reservation through GPU completion and any background checkpoint reads. Do not count CPU-offloaded or file-backed tensors as free host memory.
4. Add small deterministic parity tests for every architecture-specific layer role and operation, then test checkpoint metadata mapping and sampled payload values. On redqueen, build for the actual GPU target and qualify the real checkpoint: compare optimized output to the frozen reference, exercise image inputs when supported, run the 220,000-token boundary and smaller decode/cancellation cases, and record peak RAM/GTT, read traffic, and cache behavior. The existing mapping, dense-load, Engram, expert-cache, tiled-indexer, HIP-op, and server-contract tests provide the pattern; extend the relevant tests rather than treating startup or fluent output as qualification.

The current implementation points to [the pinned HIP bridge](hosts/redqueen/deepseek-hip/python/kernel.py), [the worker](hosts/redqueen/deepseek-hip/python/deepseek_server.py), [the checkpoint mapping audit](hosts/redqueen/deepseek-hip/python/checkpoint_mapping_audit.py), and [the dense checkpoint loader](hosts/redqueen/deepseek-hip/python/dense_checkpoint.py). Its official graph revision is pinned in `REFERENCE_COMMIT` in the HIP bridge.
